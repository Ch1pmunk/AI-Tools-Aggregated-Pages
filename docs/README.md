# docs/ —— 设计文档

这个目录回答「**怎么做到的**」。而根目录的 `Readme.md` 回答「**这个站应该是什么样**」。

> **两者冲突时以 `Readme.md` 为准。** 它是需求，这里是设计 —— 设计错了改设计，
> 需求变了才改 Readme。

---

## 一、五份文档各管什么

| 文档 | 管什么 | 什么时候读它 |
| --- | --- | --- |
| `principles.md` | **设计原则**：遇到新问题时的判断规则（网络出口、超时、缓存、验证方法…） | **改动之前先扫一眼**。它只收反复用得上、不写下来就会被忘掉的规则 |
| `architecture.md` | 三层结构、数据流、端口与 CORS、语义为什么住在 `core/`、静态服务的三张白名单、只读约束、★ 数据源开关 | 想知道「为什么这么拆」、要动结构 |
| `data-contract.md` | 端点 / 参数 / 响应 / 错误码 / 记录形状。**前后端唯一契约** | 要改接口、要加字段，**改之前必读** |
| `adapters.md` | 适配器契约、四个实现、MySQL 接入步骤与验证清单 | 要换数据源、要接 MySQL |
| `changelog.md` | 按次记录改动，含「同步了 Readme 哪几节」 | 想知道上次改了什么、为什么改 |

**契约是同一份东西的三种形式**，改一处必须同时改另外两处：

```
docs/data-contract.md            ← 给人看的
data-service/core/contract.js    ← 常量（默认值、上限）
data-service/core/normalize.js   ← 语义（归一化、匹配、排序、分页、出站投影）
```

---

## 二、其他目录也各有一份 README

「这个目录是干什么的、和谁配合」写在**那个目录自己**的 README 里，不在这里重复：

| 目录 | 那份 README 讲什么 |
| --- | --- |
| `../assets/` | 六个 js 文件各管什么、样式为什么分两处写、几个容易踩的坑 |
| `../catalog/` | 工具**记录**的字段与增删步骤（「货架上的标签」） |
| `../tools/` | 本地工具**本体**、点击卡片之后的完整链路（「货」） |
| `../data-service/` | `core/` 与 `adapters/` 的分工、一次请求经过什么 |
| `../scripts/` | 一条命令起两个服务、端口为什么只在一处配 |

根目录 `Readme.md` 是总入口，含完整的需求与目录树。

---

## 三、改动的标准动作

1. 改代码。
2. **同步 `../Readme.md` 里对应的那一节** —— 实现变了文档没变，下一轮改动的依据就是错的。
3. 契约相关的改动，同步 `data-contract.md` 与 `core/contract.js`、`core/normalize.js`。
4. 在 `changelog.md` 追加一条，写清改了什么、同步了 Readme 哪几节。

第 2 步不是形式主义：这个项目的每一轮改动都是从 `Readme.md` 出发的，
它一旦与实现对不上，下一轮就会顺着错的依据改下去。
