# 数据契约

**这是前后端唯一的契约。** 页面只认这里写的东西，数据服务只发这里写的东西。
本文件与 `data-service/core/contract.js`（常量）、`data-service/core/normalize.js`（语义）
是同一份东西的三种形式 —— **改一处必须同时改另外两处**，否则下一轮改动的依据就是错的。

> 与 `Readme.md` 冲突时以 **Readme 为准**（Readme 是需求，本目录是设计）。

---

## 一、工具记录

### 对外形状（页面收到的字段）

```json
{
  "id": "ppt",
  "name": "PPT生成",
  "description": "根据主题快速生成演示文稿，适合汇报、课件和提案。",
  "tags": ["演示文稿", "办公"],
  "icon": "📊",
  "url": "https://example.com",
  "likes": 0,
  "order": 1000
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 唯一标识。**权威来源是记录里的 `id` 字段，不是文件名** |
| `name` | string | 是 | 工具名称 |
| `description` | string | 否 | 一句话描述 |
| `tags` | string[] | 否 | 分类标签。工具页的分类筛选条由**全部启用记录**的标签派生 |
| `icon` | string | 否 | 图标（emoji 即可）。缺省由页面补 `◆` |
| `url` | string | 否 | 外链或站内地址。**只允许 http/https，或站内单个 `/` 开头的相对地址**（如 `/tools/ppt/`，指向本地项目本体）；其余归一化为空串 |
| `likes` | number | 否 | 点赞数，非负整数，缺省 `0`。**首页热门推荐的排序依据**。只读，无写入端点（见第二节「只读」） |
| `order` | number | 否 | 排序键，越小越靠前，缺省 `1000` |

### `url` 为什么放行站内相对地址

本地部署的工具本体住在本站的 `/tools/<项目名>/` 下，卡片要能直接点进去 ——
所以 `safeUrl()` 收「单个 `/` 开头」的地址。

两个必须挡掉的写法：

| 写法 | 为什么挡 |
|---|---|
| `//evil.com/x` | 协议相对地址，浏览器会当成 `https://evil.com/x`，是**外站** |
| `ppt/index.html` | 不以 `/` 开头，会相对「当前页面所在目录」解析（在 `/search` 下就变成 `/ppt/`），地址随页面漂移 |

`likes` 为什么是数字而不是布尔标记：热门推荐要有个**能被累加、能比大小**的优先级。
布尔只能表达「是/不是热门」，没有程度之分，也就排不出先后 —— 而首页那 6 张卡
今天和明天必须是同一批。这个值将来直接对应数据库里的一列。

### 存储时的额外字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `enabled` | boolean | **`false` 表示不展示。这个字段不出网** |

`enabled` 是服务端的判断依据，服务端用它筛完就不再往外发（见
`data-service/core/normalize.js` 的 `toPublic()`）。这么做有两个原因：

1. 契约说「服务端过滤」，就得真的只由服务端过滤。前端要是也拿得到它，
   迟早会有人在前端再 `filter` 一遍 —— 同一套语义两份实现，而其中一份没人测。
2. 出站字段是**白名单**。以后给记录加内部字段（缓存键、来源文件路径之类），
   不会因为忘了排除而顺带发出去。

### 记录会被丢弃的情形

单条记录坏掉**不会**升级成整个接口 500 —— 丢掉这一条、打一条日志，其余照常返回 200。

| 情形 | 结果 |
|---|---|
| 不是对象 / 缺 `id` / 缺 `name` | 丢弃，警告一次 |
| `id` 与别的记录重复 | 丢掉后来的那条，警告一次 |
| `url` 不是 http/https 也不是站内 `/…`（如 `javascript:`、`//evil.com`） | **保留记录**，把 `url` 归一化成 `""` |
| `enabled: false` | 保留记录，但**不进任何对外结果**（列表、分类计数、热门都不算它） |

日志按消息去重（见 `core/log.js` 的 `warnOnce`），所以反复刷页面不会把日志刷满。

### 排序规则（**固定的，不许各处自己定**）

```
order 升序  →  同 order 按 id 升序
```

`order` 这个字段存在的唯一理由：数据来自文件目录时 `readdir()` 的顺序由文件系统决定、
跨平台不一致。**没有确定的排序键，分页就会重复和漏项** —— 第 1 页和第 2 页之间
只要有一条记录换了位置，它就会要么出现两次，要么一次都不出现。

## 二、端点

全部 `GET`（外加一个 `OPTIONS` 兜底）。基础地址由页面解析得到，见本文第四节。

### 只读（硬性）

| 方法 | 结果 |
|---|---|
| `GET` / `HEAD` | 正常 |
| `OPTIONS` | `204`，只用于兜底 CORS |
| 其余（`POST` / `PUT` / `PATCH` / `DELETE` …） | **一律 `405`**，不看路径，不看有没有请求体 |

**没有任何写入端点，一个都没有。** `server.js` 里没有读请求体的分支，整个
`data-service/` 里没有一处 `fs.write*` —— 所以「少写了一个写接口」这种情况不是靠约定，
是在代码里就无处可写。

`likes` 因此是**静态值**：改它只能改文件。将来做点赞是**新做一套东西**
（谁能改、怎么防刷、要不要校验来源），不是在这里放宽一条限制。
在那套设计定下来之前不放宽。见 `Readme.md` 第八节「只读」。

顺带：页面的本地副本探查走 `HEAD`（`assets/js/api.js` 的 `probeLocalProject()`），
它只需要状态码、不需要响应体，`HEAD` 正好；也因此不在这张表外面。

### `GET /api/tools`

分页列表，**筛选与分页全部在服务端做**。

| 参数 | 类型 | 默认 | 上限 | 说明 |
|---|---|---|---|---|
| `q` | string | 空 | 100 字符 | 关键词。匹配范围：`name` + `description` + `tags` 拼起来做**小写包含**匹配 |
| `tag` | string | 空 | 50 字符 | 分类，**精确相等**（不是包含） |
| `page` | int | 1 | 10000 | 页码，从 1 开始 |
| `pageSize` | int | 12 | 60 | 每页条数 |

空值（缺参数、`?page=`、`?q=%20`）一律**当没传**，用默认值。

```json
{
  "items": [ /* 记录数组，最多 pageSize 条 */ ],
  "page": 1,
  "pageSize": 12,
  "total": 32,
  "totalAll": 32,
  "hasMore": true
}
```

| 字段 | 含义 |
|---|---|
| `total` | **当前 `q` + `tag` 过滤后**的条数。计数文案用它 |
| `totalAll` | 忽略 `q`/`tag`、只算启用的条数。「筛选出 n / m」里的 m |
| `hasMore` | 还有没有下一页。**由服务端算，前端不许用 `items.length < pageSize` 推导** |

`hasMore` 为什么必须由服务端给：前端那个推导只在「服务端永远是简单切片」时成立。
哪天台面加个「最后一页补齐」或者过滤掉几条不该展示的，推导当场就错，
而且错得很安静 —— 表现是「少了几张卡」，没人会想到是分页。

`items.length` 同理不能拿来当计数：它只是**这一页**的长度。

### `GET /api/tags`

```json
{ "tags": ["办公", "代码", "写作", "图像", "音频", "演示文稿"] }
```

顺序是**用得多在前，同次数按字典序升序**。定死这个规则是为了确定性 ——
否则文件读出来的顺序会泄漏到页面上，今天和明天的顺序不一样。
（mysql 版一条 `GROUP BY ... ORDER BY COUNT(*) DESC, tag ASC` 就能对上。）

### `GET /api/hot?limit=6`

首页热门推荐。`limit` 默认 6，上限 24。

```json
{ "items": [ /* 记录数组 */ ], "limit": 6 }
```

排序：`likes` 降序 → `order` 升序 → `id` 升序，取前 `limit` 条。

**次级键不能省。** 点赞数会大量并列（尤其是清一色的 `0`），只按 `likes` 排的话，
并列项的次序不受保证，同一批数据两次请求可能给出不同的 6 个。
`core/normalize.js` 的 `compareHot()` 显式写全了这三层，`mysql.js` 的
`ORDER BY t.likes DESC, t.sort_order ASC, t.id ASC` 是同一件事的 SQL 说法。

**不足 `limit` 时服务端不会凑数** —— 「槽位数」是版面事实（3 列 × 2 行），
属于页面（`HOT_SLOTS`）；服务端只管按规则给出它有的那几个。页面自己决定空的槽位怎么处理。
补数会把「本站只有 3 个工具」藏起来，而页面恰恰需要知道这件事才好画占位卡。

### `GET /api/health`

```json
{ "ok": true, "source": "json-dir", "describe": "...", "count": 32, "uptimeMs": 1650 }
```

`count` 是启用记录总数。它**真的把数据源读了一次** —— 健康检查不碰数据就说不上是健康检查。

### `OPTIONS *`

`204`，带 CORS 头。前端刻意只发「简单请求」（GET、无自定义头、无凭据），
本来不会触发预检；这个分支是给手写请求兜底的。

## 三、错误

**参数非法直接 400，不静默兜底。** 兜底会让「地址写错了」表现为「结果莫名其妙」——
那是最难查的一类问题。

一律这个形状：

```json
{ "error": { "code": "BAD_REQUEST", "message": "page 必须是 1 到 10000 之间的整数" } }
```

| 状态 | `code` | 何时 |
|---|---|---|
| 400 | `BAD_REQUEST` | 参数越界、超长、不是整数 |
| 404 | `NOT_FOUND` | 接口路径不存在 |
| 405 | `METHOD_NOT_ALLOWED` | 不是 GET/HEAD/OPTIONS |
| 500 | `DATA_SOURCE_UNAVAILABLE` | 目录不存在、mysql 连不上、mysql2 没装 |
| 500 | `INTERNAL` | 其它未预期错误 |

`message` 是给人看的中文，前端可以直接显示。**`DATA_SOURCE_UNAVAILABLE` 是页面区分
「0 条」和「不知道有几条」的唯一依据** —— 收到它，页面必须一个数字都不显示，
一个卡片都不画（含首页的虚线占位卡）。见 `Readme.md` 第十二节。

### 已经核对过的实际返回

```
/api/tools?page=0        → 400  page 必须是 1 到 10000 之间的整数
/api/tools?page=abc      → 400  page 必须是 1 到 10000 之间的整数
/api/tools?pageSize=61   → 400  pageSize 必须是 1 到 60 之间的整数
/api/tools?q=<101 字符>  → 400  q 最长 100 个字符
/api/tools?tag=<51 字符> → 400  tag 最长 50 个字符
/api/tools?q=%25         → 200  items: [] , total: 0      ← 「%」当字面量，不是通配符
/api/tools?q=%20         → 200  等同没传 q
/api/tools?limit=7       → 200  12 条（limit 是 /api/hot 的参数，在 /api/tools 上被忽略）
/api/nope                → 404  没有这个接口：/api/nope。可用：/api/tools、/api/tags、/api/hot、/api/health
POST /api/tools          → 405  只支持 GET / HEAD
OPTIONS /api/tools       → 204
```

`q=%25` 这条不是凑数的用例：**mysql 版的 `LIKE` 必须转义 `%` 和 `_`，
且要和 json 版返回同样的结果**。这是两个实现对拍时最容易分叉的地方之一。

## 四、页面怎么找到数据服务

页面**不写死**数据服务地址，按四级优先级解析（`assets/js/api.js` 的 `resolveDataOrigin()`）：

| 顺序 | 来源 | 适用场景 |
|---|---|---|
| 1 | `<meta name="data-origin" content="...">` | 数据服务在另一台机器/另一个域名。默认留空 |
| 2 | 本服务的 `GET /api/config` 里的 `data.origin` | **默认路径**。端口由服务端环境变量决定 |
| 3 | `location.origin` | 数据服务与页面同源（反向代理到同一个域名）。此时完全没有跨域 |
| 4 | 都没有 | 进入「数据不可用」态，不发任何请求（`file://` 直开走这条） |

`GET /api/config`（静态服务提供）：

```json
{
  "host": "127.0.0.1",
  "port": 3000,
  "url": "http://127.0.0.1:3000",
  "data": { "origin": "http://127.0.0.1:3001" }
}
```

前三个字段是页脚地址展示用的，一直都有；`data.origin` 是本次新增的。
**换数据服务端口不需要改任何前端代码** —— 改 `DATA_PORT`（或用 `npm start`，
它会把这个值算好传给静态服务），页面自然跟着走。

### 请求约束（改动前必须读）

页面发出的请求刻意保持「**简单请求**」：只用 `GET`、不带自定义头、不带凭据。
这样浏览器**不会发 CORS 预检**，少一次往返，也少一处可能配错的地方。

> **要加请求头或改成带凭据之前，先确认数据服务的 CORS 配置。**
> 数据服务默认发 `Access-Control-Allow-Origin: *`，而带凭据的请求**不允许**用 `*`。

### 超时

**本文件里列的每一个出站请求都必须带超时**，一个都不能漏（`fetchWithTimeout()` 是唯一入口）。
超时不是可选项：服务被关掉是秒失败（`ECONNREFUSED`），但服务**卡住**不会 ——
没有超时，页面就永远停在「正在加载工具……」，既不报错也没有重试入口。

| 请求 | 上限 | 在哪 |
|---|---|---|
| `/api/tools`、`/api/tags`、`/api/hot`、`/api/config` | 5000ms | `assets/js/api.js` 的 `REQUEST_TIMEOUT_MS` |
| 本地副本探查（`HEAD /tools/<项目名>/`） | 2500ms | 同文件的 `PROBE_TIMEOUT_MS` |

探查短一些是有意的：它只是给卡片加个角标，是锦上添花，不值得让它挂 5 秒。

**超时一到，响应被丢弃**：`AbortSignal` 把请求中止，对面后来才回的那份数据
**根本到不了页面**。这是「丢掉超时的返回」的落地方式 —— 不是靠调用方记得去判断。
（另有一道针对「成功但已经过期」的响应：筛选条件变了之后的旧响应，靠竞态令牌整包丢弃。
两道都要，挡的不是同一件事。）

超时与「连不上」在错误对象上分开标记（`err.timeout`），因为**要查的东西不一样**：
连不上是「服务没起来」，超时是「服务起来了但不应答」。页面据此挑文案，
并在超时时**额外弹一条轻提示**（状态行那行小字说不清是哪一种）。

### 本地副本探查的结果只有三种，意义各不相同

| 返回 | 含义 | 页面怎么做 |
|---|---|---|
| `true` | 200，本体在 | 正常打开 |
| `false` | **404，明确不在** | 卡片贴「本地副本未就位」，点了只给提示，不开窗 |
| `null` | 超时 / 5xx / 网络错 / 不是站内地址 | **什么都不标**，点击照旧打开，由服务端的说明页给结论 |

`null` **绝不当成 `false`**。理由和「0 条 vs 不知道有几条」是同一条：
把「没探到」说成「没有」，就是在把不确定说成事实。
探查只是提前拦一道，它**必然会漏**（探完才放进去的、网络正抖的），
所以静态服务那边的说明页（`/tools/<项目名>/` 不存在时的 404 页）是**兜底，必须留着**。
